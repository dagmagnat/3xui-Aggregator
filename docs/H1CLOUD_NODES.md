# H1Cloud и 3x-ui в 3xui Aggregator

## Защищённый режим Stage86

Для типа **H1Cloud 3x-ui** агрегатор применяет жёсткий read-only режим к inbound. Любые операции записи `/panel/api/inbounds/update/...` заблокированы на уровне серверного кода. Проверка узла, импорт, обычная синхронизация и запуск контейнера не обновляют существующих клиентов и не меняют provider-managed параметры.

Разрешены только:

- чтение готового inbound и готовых SUB/JSON-ссылок;
- создание глобального клиента и его привязка к выбранному inbound;
- удаление клиента;
- явное изменение клиентских полей: login, лимит ГБ, срок, IP-лимит, статус и комментарий.

При явном обновлении агрегатор сначала читает текущую запись клиента, сохраняет её `flow`, `subId`, ключи и служебные поля, а затем меняет только выбранные клиентские значения. Если ничего не изменилось, запрос обновления не отправляется.


## Три разных типа узла

В H1Cloud сейчас встречаются три сценария. В агрегаторе они разделены намеренно:

1. **Обычная 3x-ui** — сервер и inbound полностью контролируются владельцем. Агрегатор может создавать клиентов и, при явном разрешении, изменять параметры inbound.
2. **H1Cloud 3x-ui (панель провайдера, только клиенты)** — H1Cloud создаёт и обслуживает inbound, External Proxy/CDN и порт подписки. Пользователь может создавать клиентов, но не должен изменять inbound. Для этого сценария выбирай отдельный тип `H1Cloud 3x-ui`.
3. **H1Cloud VLESS API (`vpn main.sh`)** — отдельный скрипт с командами `vpn api`, `vpn sub`, `vpn add`. Это не 3x-ui и для него выбирается тип `H1Cloud VLESS API`.

Не смешивай токены и URL этих режимов в одной записи узла.

## H1Cloud 3x-ui: панель провайдера, только клиенты

### Что вводить при добавлении узла

Открой **Узлы → Добавить узел** и выбери:

```text
Тип узла: H1Cloud 3x-ui (панель провайдера, только клиенты)
```

Заполни:

- **3x-ui Panel URL** — адрес панели H1Cloud;
- **Panel Path** — путь панели, если он задан;
- **Метод API** — обычно API Token для 3x-ui v3;
- **API Token** — токен именно панели 3x-ui;
- **Inbound ID** — провайдерский inbound, куда нужно привязывать клиентов;
- **Порт подписки** — обычно `25555`;
- **SUB Base URL** — только если он отличается от Panel URL + порта `25555`.

Рекомендуемые опции:

```text
☑ Общий купленный трафик H1Cloud
☑ Срок клиента хранить в агрегаторе
```

### Что агрегатор изменяет и чего не изменяет

В этом режиме inbound считается **только для чтения**. Агрегатор не отправляет обратно:

- порт inbound;
- XHTTP path/mode/padding/XMUX;
- TLS/Reality;
- External Proxy/CDN;
- sniffing;
- streamSettings и другие серверные параметры.

Агрегатор управляет только:

- глобальной записью клиента в разделе **Клиенты** 3x-ui v3;
- привязкой клиента к выбранному inbound;
- включением/отключением клиента;
- локальным сроком и локальным лимитом в своей базе;
- ссылкой подписки/подключения в общей подписке агрегатора.

### Общий пакет трафика

Купленные у H1Cloud гигабайты относятся к общему пакету сервера, но сама панель H1Cloud 3x-ui требует индивидуальную квоту для каждого клиента. Поэтому агрегатор всегда записывает назначенный лимит в `totalGB`: например, два клиента по 50 ГБ делят общий купленный пакет 100 ГБ. Значение `0` используется только когда администратор сознательно назначил клиенту безлимит.

### Срок клиента

При включённой опции **Срок клиента хранить в агрегаторе** удалённая дата окончания остаётся безлимитной (`expiryTime = 0`), а срок контролирует агрегатор.

Это удобно, когда клиент уже действует, например, 10 дней из 30: при добавлении H1Cloud-узла он получает оставшиеся 20 дней по локальной дате, а не новый независимый срок в провайдерской панели.

Для надёжного отключения агрегатор должен постоянно работать и иметь доступ к панели H1Cloud.

### Как строится ссылка

Порядок получения ссылки:

1. авторизованный API 3x-ui `clients/links/:email` или `clients/subLinks/:subId` — предпочтительный способ, потому что панель возвращает точную ссылку с External Proxy;
2. публичная подписка H1Cloud через порт `25555`;
3. локальный fallback из сохранённого read-only inbound.

Для inbound с XHTTP и External Proxy публичная ссылка должна использовать CDN-адрес и порт, например:

```text
cdn.example.h1cloud.su:443
```

а не внутренний backend-порт вида `25556`. В ссылку сохраняются TLS/SNI, XHTTP path, mode и совместимые параметры `extra`.

### Ошибка `record not found` и дубли

В 3x-ui v3 клиент существует одновременно как глобальная запись и как привязка к inbound. Старый fallback API мог записать клиента только в `settings.clients`, не создав корректную глобальную запись. После этого панель отвечает:

```text
Something went wrong (record not found)
```

и может показать несколько строк с одинаковым email/UUID.

Stage75 больше не использует legacy fallback для H1Cloud 3x-ui. Но уже созданные повреждённые записи автоматически удалять опасно. Перед повторным добавлением:

1. удали **все** записи проблемного логина из оригинального раздела **Клиенты**;
2. проверь привязанный inbound и удали оставшиеся дубли;
3. если UI не удаляет запись из-за `record not found`, попроси поддержку H1Cloud очистить клиента в базе/привязке;
4. после очистки добавь узел клиенту в агрегаторе заново.

Не используй один и тот же email несколько раз в одной H1Cloud 3x-ui панели.

## Обычная 3x-ui

Выбирай **3x-ui (обычная панель)**, если inbound принадлежит тебе и его разрешено редактировать. В этом режиме доступны обычные параметры транспорта, SNI, sniffing и опция сохранения изменений в 3x-ui.

Панель может физически находиться на сервере H1Cloud, но если она не ограничена провайдером и ты полностью управляешь inbound, это всё равно обычный тип `3x-ui`.

## H1Cloud VLESS API (`vpn main.sh`)

Этот режим относится только к отдельному скрипту H1Cloud. На сервере используются команды:

```bash
vpn ports
vpn api status
vpn api token
vpn sub status
```

В агрегаторе нужны:

- **H1Cloud API Base URL**: `https://IP:API_PORT/api`;
- **H1Cloud SUB Base URL**: `https://IP:SUB_PORT`;
- **API Token**: результат `vpn api token`;
- выбор Reality/XHTTP/XHTTP CDN.

Для такого узла агрегатор получает локальные ссылки `/sub/REMOTE_UUID/local` и добавляет их в общую `/sub/:slug` и `/json/:slug`.

Самоподписанный HTTPS допускается; строгая проверка включается переменной:

```text
H1CLOUD_TLS_VERIFY=1
```

## Диагностика

Если клиент создан, но подключение закрывается сервером:

1. открой в оригинальной H1Cloud 3x-ui действие **Скопировать ссылку** и проверь её отдельно;
2. сравни публичный адрес: должен использоваться External Proxy/CDN `:443`, а не backend `:25556`;
3. проверь XHTTP path и `mode=packet-up`;
4. обнови общую подписку агрегатора после очистки дублей;
5. для Happ сначала проверь обычную `/sub/:slug`, затем `/json/:slug?format=single` для одного узла.

Если обычная ссылка панели тоже выдаёт `Сервер закрыл соединение`, проблема находится в провайдерском inbound/CDN или его текущей доступности, а не в создании клиента агрегатором.
